## Severity 1 — a reported number can be wrong

### R1. ✅ The seed and density in the headline can name a run that did not produce it
`run.py` ~240 · **the same bug class the manifest was added to prevent, only half-fixed**

`cmd_match` prints and stores `args.seed` / `args.payments_per_window`, not the values
`load_inputs` actually resolved from `manifest.json`.

**Reproduced:**

```
python run.py generate --seed 77771 --payments-per-window 12
python run.py match
  → headline reads   seed=20260905  density=6 vs 12
  → manifest says    seed=77771     ppw=12
  → run_output.json  seed=20260905  density=12   ← inconsistent with ITSELF
```

The payload takes density from `inputs.payments_per_window` (corrected) and seed from
`args.seed` (uncorrected), so it disagrees with itself as well as with the headline.

This session added `manifest.json` and a mismatch guard *specifically* to stop the
headline naming a seed that did not produce its numbers. The guard closed the loud path
and left the silent one open.

**Fix:** report from `inputs.seed` / `inputs.payments_per_window` everywhere below
`load_inputs` — the headline, `score()`, and `run_output.build()`.

### R2. ✅ The mismatch guard cannot detect an omitted flag
`src/loaders.py` ~161

The guard reads `if seed != cfg.SEED_PRIMARY and seed != on_disk`. But argparse *defaults*
`--seed` to `cfg.SEED_PRIMARY`, so an explicit `--seed 20260905` is indistinguishable from
no flag at all: the check short-circuits, the seed is silently overwritten, and the
docstring's promise to "refuse loudly on a mismatch" does not happen.

`payments_per_window` is overwritten with **no check at all**, so a density mismatch is
never reported under any invocation.

**Fix:** `default=None` as the sentinel, and check both fields.

### R3. *unverified* — `third_party_payer` is ~29% mislabelled, and I reported a number over it
`src/recon/generator/build.py` ~624 — **partially verified: 2 of 7 at seed 20260905**

The label is appended before the narration style is chosen, but the messy-narration branch
(~18%) narrates with `cust`, ignoring `third_party`. So a record is labelled as a
name-channel disagreement while carrying no disagreement at all.

Measured at seed 20260905: **2 of 7** `third_party_payer` links carry the *correct* payer
name. The `OUTCOME BY DEFECT` table — and the "4 matched, 3 refused, and the split is not
arbitrary" conclusion reported at the end of the session — are therefore computed over a
cohort that is roughly a quarter wrong. **The conclusion may survive; the evidence for it
does not, until this is fixed and re-measured.**

This is the exact defect the adjacent comment at line ~669 was added to prevent: *"a label
that can disagree with the data it describes is worse than no label."*

**Fix:** move the label below the narration choice, or condition it on which branch ran.

## Severity 2 — a command can die where it should report

### R4. ✅ The installed package is broken; only the checkout works
`pyproject.toml` ~30

`pramana` points at `run:main`, but `package-dir={"": "src"}` with
`py-modules=["config","loaders"]` never packages root-level `run.py` or the `api/` package.

**Reproduced after `pip install -e .`:**

```
cd /tmp && pramana --help        → ModuleNotFoundError: No module named 'run'
cd /tmp && python -c "import api.main" → ModuleNotFoundError: No module named 'api'
```

Load-bearing because H1 **deleted** the `sys.path` bootstrap from both files on the stated
premise that "the project installs as a package, so imports normally". The removal traded
a working checkout-only path for a broken installed path plus a CWD dependency. The claim
in the commit message is, as it stands, false.

### R5. *unverified* — the display-only compare arm can abort the whole run
`run.py` ~225

`assert_truth_is_satisfiable(cmp_batch)` is called **uncaught** on the second-density arm,
which runs on every `match` (default `HEADLINE_COMPARE_DENSITY = 12`). If that in-process
batch trips the check, the command dies with a raw traceback *after* `run_output.json` has
been written and *before* the metrics block prints — the operator loses the results of a
run that actually succeeded, to a generator assertion about a batch that exists only to
decorate the headline.

Also: the compare arm calls `match_once` even under `--verify`, so it is **un-gated** while
the primary arm is gated. The two arms are not measured the same way.

### R6. *unverified* — one bad sweep arm kills the whole sweep
`run.py` ~280

`assert_truth_is_satisfiable(batch)` is unguarded, while the **immediately following**
`assert_pool_bound` in the same loop body is wrapped in `try/except AssertionError` and
reported. One AssertionError at, say, seed 33333 / ppw 24 discards the 15+ arms already
computed. The asymmetry is in two consecutive statements.

## Severity 3 — correctness of the data and the model

### R7. *unverified* — `relation="split"` is not a member of `Relation`
`src/recon/generator/build.py` ~776

`Relation = Literal["one_to_one","many_to_one","partial","unmatched"]`. Both new
`TruthLink`s pass `"split"` positionally with **no `# type: ignore`**, unlike every other
construction in the file — so the type checker is the one thing that would have caught it,
and it was never run. It propagates into `ground_truth.json` and into the scorer's
relation buckets.

### R8. *unverified* — the statement's balance column is now arithmetically wrong
`src/recon/generator/build.py` ~761

Split parts both carry `original.balance`, so the balance never steps for part 1 and steps
twice at part 2. Chargeback debits are stamped with an **end-of-generation** running total,
then sorted into the middle of the statement by `_renumber_bank_txns`. The emitted
`bank_statement.csv` balance column is non-monotonic and wrong.

Nothing reads it today, which is exactly why it will be believed later. The generator's
stated contract is a realistic Indian bank export.

### R9. *unverified* — the ambiguity guard's "wider than the engine" margin does not exist
`src/recon/generator/build.py` ~1007

The local `lookback = cfg.SETTLEMENT_WINDOW_DAYS + 2` evaluates to 5, and
`cfg.LOOKBACK_DAYS` is also 5 — but the comment still claims it is *"deliberately wider
than the engine's rule"*. Raise `MAX_SETTLEMENT_DRIFT_DAYS` to 3 and the engine's window
widens to 6 while this guard keeps scanning 5: an interloper at lag 6 is neither detected
nor relocated, the post-condition misses it too, and **the centrepiece ambiguity guarantee
fails with nothing raising.**

### R10. *unverified* — `assert_truth_is_satisfiable` does not cover the third unreachability
`src/recon/generator/build.py` ~1244

This session made `narration_count_conflict` a hard refusal channel. A truth link marked
`assign` whose credit narrates a different transaction count is now unsatisfiable at any
tolerance — a third way to assert an unreachable link, and the assertion written to catch
exactly that class does not check it. It holds today only by construction.

### Two fixes produced further defects, which is the part worth keeping

**R6's fix had a bug of its own.** Catching the assertion meant a seed could be skipped,
but the averaging denominator was still `k = len(seeds)` — so a skipped arm would have
divided into a row it never contributed to, quietly deflating every figure in it.
Contributing seeds are now counted and short rows are annotated.

**R9's obvious fix was wrong.** Adding the "explicit margin" the review suggested made
the protected band wider than a payment's own candidate window, so a payment whose credit
sat near the ambiguity credit had its entire window swallowed and could not be relocated
anywhere legal — which made **seed 11111, one of the sweep's own seeds, unconstructible**.
The real fix is the *coupling*: read `cfg.LOOKBACK_DAYS` rather than recompute it, so the
guard tracks the engine automatically. The margin constant is kept at 0 with that
reasoning recorded, and `_relocate` now searches every legal date instead of two.
